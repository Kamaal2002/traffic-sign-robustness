# Reproduction guide

The complete workflow behind the results in
[final_test_findings.md](final_test_findings.md): environment, dataset,
verification, the nine training runs, the two evaluation stages, the two
comparison stages, the official test path and the figures. These are the
commands that produced the accepted results, and every flag is the flag the
module actually defines. The nine training runs are independent and may be run
in any order; the accepted runs were not trained in the order listed here.

Run everything from the project root. `.venv/bin/python` is written out rather
than assuming an activated environment.

## 1. Scope and reproducibility limitations

Three different things get called reproduction, and only the first is fully
supported by a clone of this repository.

**Rerunning the methodology.** Retraining the nine checkpoints and rerunning
the evaluation and comparison stages. The source, the two frozen protocols, the
pinned dependency versions and the fixed seeds are all committed, with two
exceptions, in sections 4 and 8: `src.verify_augmentation` needs the accepted
baseline checkpoint, and the official-test stage needs a checkpoint inventory
that is not committed and that no module in this repository generates.

This guide covers the three-arm comparison. It does not cover the two earlier
stages that fixed frozen augmentation parameters. `src.evaluate_robustness`
measured the clean baseline's per-family accuracy drop, with
`src.analyze_failures` and `src.plot_robustness` analysing and plotting its
saved predictions; `src.occlusion_placement`, `src.evaluate_placement`,
`src.analyze_placement` and `src.verify_placement` settled the occlusion
placement rule. Arm C's family weights and `OCCLUSION_PLACEMENT` are hard-coded
constants in `src/augmentation.py`, so retraining does not depend on either
stage, but re-deriving those constants is outside this document.

**Reproducing the reported numbers.** Not expected to match bit for bit.
`artifacts/` is Git-ignored in its entirety, so no checkpoint, per-image
prediction file, result table or comparison output is in the repository, and a
rerun starts from retrained weights rather than the accepted ones. Even with
identical code, seeds and library versions, CPU, MPS and CUDA use different
kernels and reduction orders. The accepted results were produced on MPS (Apple
Silicon) with torch 2.14.1 and Python 3.13.1.

**Regenerating the committed figures from the original analysis.** Not possible
from a clone. `src.plot_paper_figures` reads `artifacts/analysis/final_test/`,
which is Git-ignored, so those tables have to be regenerated by working through
sections 5 to 11 first. The figures themselves are committed under `figures/`.

Two further constraints shape the order below.

`docs/final_test_protocol.md` is pinned by SHA-256 inside
`src/evaluate_test.py`. A run whose protocol document has changed by a single
byte stops rather than proceeding, which is the point of freezing it before any
test number existed. The same holds for the augmentation protocol through
`docs/augmentation_manifest.json`.

The official-test path in sections 9 to 11 is one-shot by design. It refuses to
start if `artifacts/final_test/` already exists, and the post-run check needs
the pre-run integrity snapshot. Working through it twice means deciding
explicitly what to move aside, not rerunning the commands.

## 2. Environment and dependencies

Python 3.13 with the pinned versions in `requirements.txt`.

```sh
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
```

The accepted runs used torch 2.14.1, numpy 2.5.3 and pandas 3.0.6 on macOS,
with device `mps`. Every training and evaluation entry point accepts
`--device`; the `verify_*` modules do not. Left unset, `select_device()` takes
`cuda` first, then `mps`, then `cpu`, so the accepted device is what a machine
without CUDA selects.

## 3. Dataset acquisition

`data/` is Git-ignored and the dataset is not shipped with the repository.
Nothing in `src/` enables torchvision's `download` flag, so no module will
fetch it: `create_data_loaders` defaults to `download=True` but every call site
inside `src/` overrides that with `download=False`. The archives were fetched
once through `notebooks/01_data_exploration.ipynb`; these two lines do the same
thing in a fresh clone.

```sh
.venv/bin/python -c "from torchvision.datasets import GTSRB; \
GTSRB(root='data', split='train', download=True); \
GTSRB(root='data', split='test', download=True)"
```

This populates `data/gtsrb/GTSRB/Training` with 26,640 images in 888 tracks
and `data/gtsrb/GTSRB/Final_Test/Images/` with the 12,630 official test images.
The labels arrive separately, at `data/gtsrb/GT-final_test.csv`, which is where
`src.evaluate_test` resolves them; the `GT-final_test.test.csv` inside
`Final_Test/Images/` is the unlabelled file shipped in the image archive.

## 4. Data and model verification

Four modules check the pipeline, the model, the corruption families and the
augmentation policies. None of them trains anything. The first three run as
soon as `data/` is populated:

```sh
.venv/bin/python -m src.verify_data_pipeline
.venv/bin/python -m src.verify_model
.venv/bin/python -m src.verify_corruptions
```

The fourth needs an artifact that is not committed, so it will fail on a fresh
clone:

```sh
.venv/bin/python -m src.verify_augmentation
```

`src.verify_data_pipeline` and `src.verify_model` take `--batch-size`; the
other two take no flags.

Two things to know about these.

**`src.verify_data_pipeline` reads 64 official test images on every run.** It
iterates `next(iter(loader))` for every split `create_data_loaders` returns,
the test split included, to assert batch shape, dtype, pixel range and label
range. It constructs no model, runs no forward pass, computes no prediction and
writes no file; its entire output for the test split is a shape, a dtype and
two ranges. The official test split is therefore not completely untouched, and
Part 8 of [final_test_protocol.md](final_test_protocol.md) is the standing
record of that access. `src.verify_model` deliberately iterates only `train`
and `validation`.

**`src.verify_augmentation` does not run on a fresh clone.** Its provenance
check requires `artifacts/baseline/best_checkpoint.pt` at the MD5 pinned in
`src/evaluate_robustness.py`, which is the accepted baseline checkpoint and is
not committed. It passes against that file and not against a retrained one.

`src.verify_data_pipeline` prints the track and image counts the rest of the
study depends on: 888 tracks of 30 frames, 710 training tracks and 21,300
training images, 178 validation tracks and 5,340 validation images, zero track
overlap, and 12,630 official test images.

## 5. Training the nine checkpoints

Three entry points, 30 epochs each, one output directory per run.

```sh
.venv/bin/python -m src.train                   # arm A, seed 42, the baseline
.venv/bin/python -m src.train_clean --seed 43
.venv/bin/python -m src.train_clean --seed 44
for policy in balanced targeted; do
  for seed in 42 43 44; do
    .venv/bin/python -m src.train_augmented --policy "$policy" --seed "$seed"
  done
done
```

The directories are `artifacts/baseline`, `artifacts/clean_seed43`,
`artifacts/clean_seed44` and `artifacts/augmented_<policy>_seed<seed>`.

`src.train` takes `--epochs --batch-size --learning-rate --weight-decay --seed
--device --output-dir --smoke-test`. `src.train_clean` takes a required
`--seed` plus `--epochs --batch-size --device --output-dir --smoke-test`.
`src.train_augmented` takes a required `--policy` (`balanced` or `targeted`)
plus `--seed --epochs --batch-size --device --output-dir --num-workers
--smoke-test`.

### Output-directory behaviour

This is where accepted results are easiest to destroy, so the three entry
points differ deliberately.

`src.train` has no guard. It calls `output_dir.mkdir(parents=True,
exist_ok=True)` on `artifacts/baseline` and would overwrite an accepted
baseline in place. Run it only when that directory is absent, or pass
`--output-dir`. It was kept as close as possible to the code that trained the
baseline, which is why the guard went into the newer entry points instead.

Close is not identical. The module's one committed change, in commit
`fc90073`, split `per_class_from_confusion` out of `metrics_from_confusion` so
that failure analysis and the headline numbers read the same per-class vector.
The refactor moved no arithmetic: accuracy is still the diagonal sum over the
matrix sum, and macro F1 is still the mean of the same float64 per-class
expression over all 43 classes with the same zero-denominator convention.
`src.verify_training` exercises the refactored path, since
`metrics_from_confusion` now calls `per_class_from_confusion`, and cross-checks
its macro F1 against `sklearn.metrics.f1_score` to within 1e-12 three times:
on synthetic predictions spanning all 43 classes, on real validation
predictions from an untrained model, and on a constant-majority predictor.

The accepted baseline checkpoint predates one further difference, recorded in
[../src/README.md](../src/README.md): it was written before `train.py` read the
loss, optimizer and schedule off the constructed objects, so its metadata is in
the older layout. That change adds checkpoint fields and touches no measured
quantity. The checkpoint was reused for arm A at seed 42 rather than retrained,
so no reported number depends on rerunning this module at all.

`src.train_clean` and `src.train_augmented` both claim their directory through
`claim_output_dir`, which runs `check_output_dir` and only then creates the
directory, so a refused run leaves no empty directory behind.
`check_output_dir` refuses a directory inside `artifacts/baseline` or
`artifacts/robustness`, a directory that contains either of them, and any
directory already holding `best_checkpoint.pt`, `history.json`, `policy.json`
or the protocol sidecar. Separately, `src.train_clean` refuses `--seed 42`
without `--output-dir` before the directory check is reached, because arm A at
seed 42 is the accepted baseline rather than something to retrain.

`src.verify_training` is the training stage's pre-flight check: an optimizer
step moves parameters, BatchNorm statistics freeze in validation, validation
leaves the model untouched, the official test loader is never iterated, and a
captured checkpoint is decoupled from the live model. Unlike the section 4
checks it trains, running a two-epoch smoke run into `artifacts/smoke`.

### Smoke tests

`--smoke-test` shortens a run to two epochs over five batches per phase, and it
behaves differently per module. Only `src.train` redirects the output, to
`artifacts/smoke`. `src.train_clean` and `src.train_augmented` still target the
seed's own directory, so pass `--output-dir` as well:

```sh
.venv/bin/python -m src.train_augmented --policy targeted --seed 43 \
    --smoke-test --output-dir artifacts/smoke_augmented/targeted
```

Without it, the smoke run cannot overwrite a finished run — the artifact check
refuses that — but run before one it claims the directory the real run needs,
which then has to be cleared by hand.

## 6. Validation-stage corruption evaluation

One call per checkpoint and suite, eighteen in total.

```sh
.venv/bin/python -m src.evaluate_checkpoint \
    --checkpoint artifacts/augmented_balanced_seed42/best_checkpoint.pt \
    --suite frozen
```

Repeat with `--suite heldout`, and for each of the nine checkpoints. Flags:
`--checkpoint` and `--suite` are required; `--model-name --output-dir --device
--batch-size --num-workers --smoke-test` are optional.

Results land in `artifacts/robustness/<arm>_seed<seed>/<suite>/`, holding
`summary.csv`, `summary.json`, `per_class_metrics.csv`,
`confusion_matrices.npz`, `predictions.csv` and `metadata.json`. The arm label
comes from the `policy.json` beside the checkpoint; the arm-A runs have no
`policy.json` and fall back to `clean`, so `--model-name` is an override rather
than a requirement. The module refuses to evaluate into a directory that
already holds results.

The metadata written here matters later. Section 8's inventory check reads
`artifacts/robustness/<arm>_seed<seed>/<suite>/metadata.json` back to bind each
checkpoint to its arm and seed, and requires it to carry a
`clean_reproduction` block, a `checkpoint.recorded_validation_metrics` block
and `integrity.clean_metrics_match_checkpoint_record: true`.

## 7. Validation comparison

All nine cells in a single call, as `--model <arm>:<seed>:<directory>`. A shell
helper keeps the eighteen arguments readable and is reused in section 11:

```sh
models() { for arm in clean balanced targeted; do for seed in 42 43 44; do
    printf -- '--model %s:%s:%s/%s_seed%s ' "$arm" "$seed" "$1" "$arm" "$seed"
  done; done; }

.venv/bin/python -m src.compare_models $(models artifacts/robustness)
```

`--model` is required and repeatable; `--output-dir` is the only other flag.
Output goes to `artifacts/analysis/augmentation/`, including
`arm_error_rates.csv`, `paired_contrasts.csv`, `per_family_contrasts.csv`,
`per_severity_contrasts.csv` and `across_seeds.csv`.

This stage is a prerequisite for section 11, not an optional diagnostic:
`src.compare_test` reads `artifacts/analysis/augmentation/across_seeds.csv` to
build `validation_reproduction.csv` and has no flag pointing elsewhere.

## 8. Official-test prerequisites and the checkpoint inventory

`src/evaluate_test.py` will only evaluate a checkpoint listed in
`artifacts/robustness/checkpoint_inventory.json` whose MD5 and SHA-256 both
match the recorded digests. That file lives under the Git-ignored `artifacts/`
tree, so it is not in the repository, **and no module in this repository
generates it.** A fresh clone cannot proceed past this point without writing
its own inventory by hand.

That is a real gap in the reproduction path, not a step that was left out of
this document. The inventory for the accepted runs was recorded while the
validation stage was still live; nothing was written to regenerate it, and
nothing here invents a command that does not exist.

What the file has to contain, as read by `inventory_record`,
`check_inventory_digests` and `check_validation_binding`: a `models` list of
nine records, each with `checkpoint_path` (the repository-relative path, which
is what the lookup keys on), `checkpoint_md5`, `checkpoint_sha256`, `arm_label`
and `seed`. The accepted file also carries `recorded_at`, `repository_head`,
`protocol`, a `note`, and per-record provenance fields, which the test stage
copies into its metadata.

The digests must be the bytes of the checkpoints the section 6 validation
results were measured from, and section 6's metadata must still be present and
must record the same MD5. Retrained checkpoints will not carry the digests in
the accepted inventory, so an inventory written for a rerun describes that
rerun's own nine files and binds to that rerun's own validation metadata.

## 9. Final-test integrity checks

```sh
PYTHONPATH=. .venv/bin/python -m src.verify_test_path \
    --record-snapshot artifacts/final_test_integrity/pre_run_snapshot.json
```

This records digests of the validation artifacts and the nine checkpoints
before any test inference. The module is not itself blind to the test split:
checks authorised by Part 10 of [final_test_protocol.md](final_test_protocol.md)
parse the official `GT-final_test.csv`, list the 12,630 test `.ppm` files, MD5
the three GTSRB archives and SHA-256 every test image's bytes. No official test
image is decoded and no test metric is computed — the checks that do run a
model run it on synthetic images — and tripwires on `GTSRB.__getitem__` and
`evaluate_test.build_test_observations` make an accidental real read fail
loudly.

`--record-snapshot` refuses an existing file. In its default pre-run mode the
module also checks that `artifacts/final_test/` does not exist yet, which is
what makes the sequence one-shot.

`src.verify_test_path` takes `--record-snapshot`, `--verify-snapshot` and
`--post-run`. `--post-run` refuses to run without `--verify-snapshot`.

## 10. Official-test execution

```sh
PYTHONPATH=. .venv/bin/python -m src.run_final_test
PYTHONPATH=. .venv/bin/python -m src.run_final_test --execute
PYTHONPATH=. .venv/bin/python -m src.verify_test_path --post-run \
    --verify-snapshot artifacts/final_test_integrity/pre_run_snapshot.json
```

Without `--execute`, `src.run_final_test` prints the plan and exits: nothing is
run, nothing is created, and no official test image is read. It does read the
checkpoint inventory and recompute the nine checkpoint digests, which is how it
validates the plan, so a missing or stale inventory fails here rather than
part-way through the runs.

With `--execute` it works through the eighteen evaluations in a fixed order,
writing `artifacts/final_test/<arm>_seed<seed>/<suite>/` and appending to
`artifacts/final_test/test_access_log.jsonl`. The eighteen runs took 2 h 29 min
of wall-clock on the machine used here. Flags: `--execute --device
--output-root --log-dir --resume --skip-digests`.

`src/evaluate_test.py` refuses to write into `artifacts/baseline`,
`artifacts/robustness` or `artifacts/analysis`, and refuses any non-empty
output directory, so a run that stopped part-way has to be examined and moved
by hand rather than completed over the top of itself.

## 11. Final-test comparison

```sh
.venv/bin/python -m src.compare_test $(models artifacts/final_test)
```

Same `models()` helper as section 7, pointed at the test results. Output goes
to `artifacts/analysis/final_test/`: `arm_error_rates.csv`,
`paired_contrasts.csv`, `across_seeds.csv`, `per_family_contrasts.csv`,
`per_severity_contrasts.csv`, `per_class_recall.csv`,
`class_balanced_error.csv`, `class_balanced_contrasts.csv`,
`clean_performance.csv`, `clean_tradeoff.csv`,
`design_effect_sensitivity.csv`, `validation_reproduction.csv`,
`comparison.json` and `comparison.txt`.

Bootstrap intervals are 2,000 paired image-level resamples at seed 42, reported
as percentile intervals. They assume independent image-level sampling, which
the repeated frames of each physical sign violate, so they are not
population-level confidence intervals and none of them enters the success
criterion.

This stage fails without `artifacts/analysis/augmentation/across_seeds.csv`
from section 7.

## 12. Figure generation

```sh
.venv/bin/python -m src.plot_paper_figures
```

Reads `artifacts/analysis/final_test/` and writes a PDF and a PNG for each of
the four figures into `figures/`. `--analysis-dir` and `--figure-dir` move
either end.

The script recomputes no error rate and no interval. The only aggregation it
adds is the mean across the three seeds, taken over the per-seed rows of
`arm_error_rates.csv` for Figure 1, `per_family_contrasts.csv` for Figure 2 and
`per_severity_contrasts.csv` for Figure 3. Figure 4 adds no aggregation: it
plots the nine checkpoints individually.

It stops if the analysis directory does not record the official test split,
since the validation stage writes tables under the same names and pointing
`--analysis-dir` at `artifacts/analysis/augmentation/` would otherwise produce
figures labelled for the test split from validation numbers.

## 13. Known limitations and troubleshooting

**The inventory gap is the hard blocker.** Section 8 is the one step a fresh
clone cannot complete from committed material. Everything before it runs;
everything after it depends on it.

**The official-test path cannot simply be rerun.** `--record-snapshot` refuses
an existing snapshot file, the pre-run check refuses an existing
`artifacts/final_test/`, and `src/evaluate_test.py` refuses a non-empty output
directory. All three are deliberate. Rerunning means moving the previous
results aside as a conscious decision.

**A changed protocol document stops the test stage.** If
`docs/final_test_protocol.md` no longer hashes to
`41df8eef10ae5d736d203245bfce1156c0ef57c51ee41e0574ba6a5e8eff07ef`, or the
augmentation manifest no longer matches its protocol, the run stops. Do not
edit either document to get past this.

**`src.verify_augmentation` failing on a fresh clone is expected.** It needs
the accepted baseline checkpoint at a pinned MD5, which is not committed.

**Comparison stages fail on a partial set.** Both expect all nine cells in one
call, for both suites. Point `models()` at the right directory root —
`artifacts/robustness` for section 7, `artifacts/final_test` for section 11.

**Numbers that differ after retraining are expected, not a bug.** See
section 1. Compare directions, seed consistency and the success criterion
rather than digits.
